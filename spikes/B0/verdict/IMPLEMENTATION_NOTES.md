# verdict_b0.py — implementation notes (ambiguities and literal readings)

Tool version 1.0. PLAN `spikes/B0/PLAN.md` sha256 `ed6b6a54a860bbfc67d7c822b5394804b8d408f6aae57fbeb118d2ea63c52557`.
Each item gives the PLAN section, the ambiguity, and what the tool does.

1. **§5 TB rules + §3.3/§6.3 (a) NaN test.** The PLAN does not say whether the NaN/inf test runs on raw records or after the duplicate-step rule. The tool applies "latest wall time wins" first (a general extraction rule) and then tests the de-duplicated values. If an attempt dir holds more than one event file, all of them are merged for classification evidence, and V-1 / integrity fail on the file count.
2. **§3.3 "final exception line of the traceback".** The final line is the first non-indented, non-empty line after a `Traceback (most recent call last):` body. In a chained traceback ("During handling…" / "The above exception was the direct cause…"), only the last traceback's final line counts. A traceback is "before the scoring endpoint" when its `Traceback` header line comes before the first line starting `it 1600 |` (or when there is no such line). Every pre-endpoint traceback is tested, not only the last one.
3. **§3.3 OOM row.** The PLAN gives no pattern. The tool matches the pre-endpoint final exception line against `(?i)out[ -]of[ -]memory|OutOfMemoryError`.
4. **§3.3 SEAM row ("any seam prints unverified or false").** Before the endpoint: a non-detail `[seam]` line with any `key=false` or `key=unverified` value, or any `[seam]` line containing `unverified`. `[seam] Sx detail …` lines are not searched for `false`.
5. **§4.3 completion condition from the bundle.** Completed means all of: the train log has a line starting `it 1600 |`; `meta/harness_stop_<AID>.txt` says `ckpt_stable=true` and `harness_stop_timeout` is not `true`; `logs/attempts/<AID>/junior_policy.json` exists; and the harness record's `sidecar` is not `missing`. A missing harness_stop file means the attempt is not completed, because checkpoint stability cannot be shown. `harness_stop_timeout=true` always means INFRA (§4.3 step 3).
6. **§3.3 / §6.4 INFRA cap.** The cap is exhausted when 2 of a cell's first two attempts are INFRA. This applies to every gate-arm cell, including `b0` cells that a retry pair later replaces and `b0lr05` cells. A third attempt, or an attempt after the scored one, is reported in `cells.<cell>.notes`.
7. **§6.1 V-1…V-4 for an empty slot.** If a gate slot has no scored attempt and no terminal divergence (the cell was never run, or a needed retry pair is absent) and the spend cap was not hit, the PLAN has no explicit row. The tool marks V-1, V-2, V-3 and V-4 false for that slot, which gives row 1 BLOCKED. If the spend cap was hit, `spend_cap` is listed as well.
8. **§6.3 retry pair trigger.** If any attempt in either `b0` gate cell of seed s diverged (class DIV, or completed with divergence (a)), both slots at seed s take the `b0lr05` cells. Any divergence of a `b0lr05` attention or mlp_matched attempt at that seed is terminal. `b0lr05` cells that have no matching `b0` divergence are ignored for scoring and listed under `cells`.
9. **§6.4 checkable gate runs, terminal attention run.** Integrity checks: attempt dir present, exactly one tb file, train log present, divergence evidence (a non-finite value at step ≤ 1600 in the single tb file, or an R-DIV final line before the endpoint), V-2(b) argv, V-2(c) GPU, and V-3 seams. The V-3 descriptor-identity check, which is not a seam, is applied to that run only if its sidecar is present.
10. **§6.1 V-4 content checks.** The eval `exit=` code is recorded but is not a content check, since §4.4 says the scored execution is the first that passes "V-4's content checks". "eval.log names the matching checkpoint path" means every `[eval_entry] … --ckpt <p>` line in that eval.log has `<p>` equal to `logs/<RUN>/ckpt_<IT>.pt`, or ending in `/` + that path, or equal to the `meta/ckpt_map.txt` path for (AID, it<IT>). A mask JSON is found by the suffix `_mask<f>.json` in the exec dir, and there must be exactly one per mask.
11. **§6.1 V-0.** Passes iff at least one `train_up_sanity.log` exists across the deposits, and every one present contains `[INFO] max_hours reached, stopping` and no `Traceback`. `driver_state.txt` `V0` records are not used as evidence.
12. **§6.1 V-2(c).** The GPU name is parsed from each deposit's `meta/nvidia-smi.txt` GPU row (`|   0  NVIDIA L4 … Off |`). V-2(c) needs one non-empty, identical name across all opened deposits. The §2.3 "T4 is not allowed" rule is not turned into a gate; `gpu_name` is reported.
13. **§2.3 venue mixing.** §2.3 says mixing venues makes the run set BLOCKED, but §6.4 row 1 does not list it. The tool adds row-1 item `venue_mixed` when the `meta/session.txt` venues, the seal `DEPOSIT <venue>` tokens and `--venue` are not all the same.
14. **§6.4 row 1 vs BUNDLE_CONTRACT `BLOCKED.md`.** `BLOCKED_REASON=spend_cap` feeds only the spend-cap predicate. `R1_unresolved` becomes the row-1 item "R1 unresolved", and so does `meta/torch_cuda.txt` = `cuda False`. `tarball_sha_mismatch` becomes `deposit_check`. Any other code (`cpu_test_mismatch`, `setup_failed`, `plan_gap`) becomes a row-1 item `blocked_md:<code>`, because the runner declared a plan gap (§3.4 / method §12.2).
15. **§4.1 step 2 / §8.2 tarball hash.** Every opened deposit must have `meta/tarball_sha256.txt` whose first token equals `--tarball-sha`. If it is missing or different, the item is `deposit_check`.
16. **§8.2 seal check.** A deposit is sealed if some seal-log line has the token `DEPOSIT` followed by `colab` or `xn4090`, with the deposit's sha256 as a later token on that line. The seal venue does not have to equal `--venue` for this check (see item 13). An unsealed deposit is not extracted. Members are rejected (whole archive not extracted) for: absolute paths, `..` components, `*.pt`, symlinks or hardlinks that point outside the archive or at `*.pt`, and special files. Extraction uses `tarfile` `filter="data"`, and extracted files are set to mode 0444.
17. **§8.3 `failing_ids` outside row 3.** Rows 1, 2 and 4 have `failing_ids = []`. Row-1 items are in `blocked_reason` as short codes (`V-0`, `R1_unresolved`, `OOM`, `SEAM`, `INFRA_cap`, `V-1`…`V-4`, `terminal_comparator_divergence`, `F2_none_divergence`, `spend_cap`, `deposit_check`, `venue_mixed`, `blocked_md:<code>`). Human-readable details are in `blocked_detail`.
18. **§5 `rh_clips_over_T`.** The PLAN does not say which records are counted. The tool counts clip records with `steps > 500` over every scored eval execution of every completed attempt (all checkpoints, all masks, gate and reference).
19. **§6.2 shadow verdict outside row 4.** Row 4: the same rules on R_step. Row 2: `shadow_outcome_rstep = INFERIOR`, because terminal divergence is metric-independent. Rows 1 and 3: `null`. `metric_disagreement` is true only when both outcomes are non-null and differ. The R_step comparison numbers are in `shadow_raw`.
20. **§5 M-9.** `W_hours` is `null` unless all 6 scored gate slots have `time/hours` at it 1600. The terminal attention run counts as a slot, so W is `null` in row 2 whenever that run stopped before it 1600. A per-run value is `null` if W < hours at it 400 or any bracketing value is missing. If two checkpoints have equal hours, the later checkpoint's R_H is used.
21. **§6.1 L-1/L-2 windows.** First 5 = the first 5 logged points (step ≤ 1600) with `time/updates ≥ 20`. Last 5 = the last 5 logged points with step ≤ 1600. If a window has fewer than 5 points, the value is `null` and the run counts as not passing.
22. **§8.1 multiple deposits.** Files from all opened deposits are merged by relative path, ordered by `meta/session.txt` `part` and then CLI order. A later part wins a duplicate path, and duplicates are listed in `duplicate_members_across_deposits`.
23. **§3.3 post-endpoint anomalies.** The `KeyboardInterrupt` traceback that the harness SIGINT normally causes comes after the endpoint. It is recorded literally as a `post_endpoint_anomaly` (kind `exception_after_endpoint`) on every completed attempt.
24. **§6.4 "gate set complete".** Each of the 6 slots has either a completed scored attempt with a scored eval execution at all 4 checkpoints, or a terminal attention divergence.
25. **§5 M-6.** `clip_fraction_last25` is always `null`: F-4 records `m6_evaluable=false` and no per-update clip indicator, so clause (b) is skipped (`DIV.clip_clause_b`). `grad_norm_max` is the max finite `policy/policy_grad_norm` at steps ≤ 1600.
26. **§6.4 / §8.3 REF rows without a scored reference attempt.** `pass=false`, with `status` = `incomplete` only when the spend cap was hit after the gate set was complete. Otherwise `status` is `missing` (no attempt) or `not_completed`. REF-1 additionally needs no divergence of the reference run.
27. **§8.3 `harness_stop`.** This is the boolean `harness_stop` from `meta/harness_stop_<AID>.txt` (true iff SIGINT was sent). The full record is in `harness_stop_record`, and the derived completion inputs are in `completion`.
28. **§8.3 `eval.it<IT>` key.** This is nested as `attempts.<AID>.eval.it0000400` … `it0001600`, each with `scored_exec` and `mask0.00/0.10/0.20` (plus an `executions` map with per-exec problems). `rho_h`/`rho_step` are present only for masks > 0 and are `null` on a zero denominator.
29. **§8.3 output line formatting.** Floats are printed with Python `repr`, `None` is `null`, and lists are comma-joined without spaces.
30. **§5 TB CRC handling.** TFRecord CRCs are verified. A record with a bad data CRC is skipped, and a bad length CRC or a truncated tail stops reading that file. Both are reported in `tb_read_info` and are not gates by themselves.
31. **§8.3 `budget.updates_at_1600`.** This lists the scored-set slot attempts, including a terminal attention run (its value may be `null`). `parity` is V-2(a), computed over the fully checked runs only.
